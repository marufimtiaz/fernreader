## What 8.1 and 8.2 deliver (`core/epub`, package `chunk` and `cfi`)

- `Cfi`: parse/format of EPUB CFIs (points and ranges); assertions and terminals are kept byte for byte, so a CFI
  written by foliate-js prints back unchanged.
- `ChunkMap : PositionMap`: CFIs, hrefs and text offsets both ways between original and virtual documents.
  - Spine steps count every element child of `<spine>` (what foliate-js does: `CFI.fromElements`), while section
    and text indices count only real sections (`BookPackage.spine`, foliate's `sections`). An unknown idref keeps
    its slot.
  - Container-child step shift by `2 * childOffset`. The container is the body, or its single wrapper element.
    Text before the wrapper is in part 0, text after it in the last part.
  - Original CFIs get the split itemref's `[id]` back, so they look exactly like CFIs written on the unsplit book
    (rows from M2..M7 resolve as they are).
  - Ranges keep the reader's parent/start/end split. A stored range that crosses a cut under the current policy
    is clamped to the end of its first part for display; the stored range itself is not changed.
- `SplitPlanner`: one forward scan, no DOM. It cuts only after complete container children. It splits only
  documents an XML parser accepts as XHTML. Otherwise foliate-js re-parses them as HTML (epub.js `loadDocument`),
  which can build other children, so the planner refuses (identity) on any of:
  - a scanner error;
  - a mismatched, stray or missing end tag, including unclosed void elements;
  - a root that is not `html` in the XHTML namespace;
  - an HTML named entity without an XHTML public doctype, or a bare `&`;
  - a `<` outside CDATA in script or style;
  - an undeclared namespace prefix;
  - anything after the root.

  A last part under half the target joins the part before it.
- `Chunker` (policy: threshold 512 KB, parts of about 128 K characters; `ChunkPolicy.key` names the cache):
  - Splits only present, reflowable `application/xhtml+xml` spine items, never the nav document.
  - Parts repeat the original prolog and `<head>` (and the wrapper's start tag), so CSS and namespaces still apply.
  - Rewrites, through the shared scanner, every document that links into a split one: content documents, nav, and
    NCX `<content src>`. Inside parts, `#id` links that point to another part are retargeted too.
  - The OPF: each split itemref becomes one itemref per part (other attributes kept), and one manifest item per
    part is added (media type and properties of the original). The original item stays. Guide references are
    retargeted.
  - Rewritten documents are written as UTF-8 with their declared encoding changed to match. Documents are read with
    `TextDecoding.decodeExact`: if a document that would have to be split or rewritten is in an encoding we cannot
    decode exactly (e.g. Shift_JIS, or undeclared non-UTF-8), the book stays unsplit.
  - Part names are `name.partN.ext`, never clashing with zip entries. Hrefs are percent-encoded, so
    `big%20chapter.xhtml` works.
- `ChunkStore` (`MemoryChunkStore`, `FileChunkStore` with temp file + rename, hashed file names), `ChunkedBook`
  (`virtualEntry(path)`: null = serve the zip entry). The cache commits with `cache.json` written last
  (policy key, central-directory digest, spine slots, map, and the byte size of every entry). Any of these causes a
  rebuild: a changed file, a changed policy, a damaged `cache.json`, or an entry that is missing or has the wrong
  size. The result "nothing to split" is cached too. A virtual entry that disappears while the book is open throws
  `ChunkCacheException`; it is never answered from the zip.

## Review (whole branch, 3487f72..de36b3f) and fixes

The reviewer found no Critical issues, three Important ones and seven Minor ones. All three Important issues are
fixed, each with a pinning test:

1. **Documents the reader parses as HTML were split.** Unclosed `<br>`, `&nbsp;` without a doctype, no namespace
   and similar all send foliate to its HTML fallback, and its child counts differ from the scanner's. The
   reviewer's probe shifted positions by about three times. The planner now enforces the XML rules listed above.
   Pinned by `SplitPlannerTest.documents_the_reader_would_parse_as_html_are_not_split` and `xml_safe_variants_are_split`.
2. **Unsupported encodings were corrupted.** Text was decoded as UTF-8 and the declaration rewritten. Added
   `TextDecoding.decodeExact`; such books stay unsplit. Pinned by
   `ChunkerTest.documents_in_encodings_we_cannot_decode_are_left_alone` and
   `TextDecodingTest.exact_decoding_refuses_what_decode_would_garble`.
3. **A partly deleted cache was served as complete,** and a missing virtual entry fell back to the original zip
   entry. `cache.json` now records entry sizes, and a mismatch rebuilds. A virtual entry that vanishes throws.
   Pinned by `ChunkerTest.cache_with_missing_or_truncated_entries_is_rebuilt` and
   `a_virtual_entry_that_disappears_is_an_error_not_the_zip_entry`.

Minor issues fixed:
- Unmappable cross-part or cross-document ranges now clamp or collapse to the mapped start; before, the original
  CFI came back unchanged.
- A bare section CFI (`/6/N`) of a later part maps to that part's first element.
- Ranges whose start and end are only a terminal keep their shape.
- Links in another percent-encoding (lowercase hex) are retargeted: names that are not plain ASCII skip the
  prefilter.
- The negative result is cached.
- The OPF rewrite looks for `<spine>` only directly under the root.
- The huge-chapter wall-clock bounds are loosened against CI noise.

Minor issue left open:
- A full fsync per part: size checks cover the power-loss case, and 80 fsyncs would cost open time.

## What 8.3 delivers

What the user sees: the huge single-chapter book (10 MB, one XHTML) now opens in about 0.6 s instead of tens of
seconds (P-014: 617 ms median from the library; 437 ms for the very first open, chunking included). Rotation on it
takes about 0.3 s, and "MARKERWORDHUGE" finds all 138 hits in under 0.5 s. Reading positions, bookmarks, highlights,
notes, search hits, the Contents/Bookmarks/Highlights lists and Back history behave as in any other book, and land
on the same text as before chunking. Rows saved before M8 (M2..M7, unchunked) still resolve. Books with nothing to
split open exactly as before (no package parse, no cache directory).

- `BookOpener` (`app/.../reader/BookOpener.kt`, `BookSession.kt`):
  - Fast path: books without an `.xhtml/.xht/.html/.htm` entry over the threshold (512 KB) skip chunking entirely.
  - Otherwise it parses the package once (`PackageLoader`). It runs `Chunker(policy).chunk(...)` only when
    `Chunker.hasCandidates` says so. A later open reads the complete cache.
  - Any exception, or an `OutOfMemoryError`, while chunking opens the book unsplit with the identity map.
  - The map reaches the controller through `OpenResult.Ok.map`.
  - A warm reopen (P-016) keeps its chunked book; a session opened under another policy is not reused.
- `BookContentServer` serves `virtualEntry(path) ?: zip entry`. `entries.json` lists the zip entries (virtual
  sizes for rewritten ones) plus the parts.
  - On `ChunkCacheException` (cache trimmed while open), the session rebuilds the cache once, under a lock, with
    the same policy and zip, so it gets the same map.
  - A failed rebuild (e.g. ENOSPC, OOM) is remembered: later requests answer 500 at once.
  - A virtual path is never answered with the zip entry, and `BookPathHandler` answers 500 for any Throwable.
- Chunk directory: `cacheDir/chunks/<sha256(SourceRef.key)[0,32)>/<policy.key>/`, created on the first write.
  - `StorageManager.setCacheBehaviorGroup(dir, true)` makes the system trim it only whole.
  - It is deleted with the book on the M7 delete path, next to `LibraryDao.deleteCache`. It is also deleted when
    a missing file is forgotten and when open-with session files are dropped.
  - A delete waits for a rebuild in flight, and a deleted book's session never rebuilds.
  - A moved file gets a new key: the old directory is left for the system to trim.
- `ReaderController`: every CFI and text position crosses `Session.map`.
  - Stored data (positions, bookmarks, annotations, and so backups) is original.
  - Everything sent to the web side is virtual.
  - Annotation lists sort on original CFIs.
  - Two gaps fixed:
    - search-hit chapter labels now use the virtual section;
    - M4 section stats are cached per layout (`book_cache` kind `section-stats.v1@<policy>` for chunked books).
  - Back history and footnotes use virtual hrefs and are never persisted.
- Database: `book_cache` exists since schema 4 and its (bookId, kind) key already separates layouts. The chunk
  cache checks itself through `cache.json`. So the schema stays at **7** (Q6).
- reader-web (found by the device test, an M6 bug): a highlight on exactly the search hit's range was erased
  together with the search outline. It is now drawn again when the outline is cleared (vitest pins it).

Tests:
- JVM: `ReaderControllerChunkTest` (6 tests, a real `ChunkMap` with a small policy); chunk tests for
  `BookOpener`, `BookContentServer` and `ChunkDirs`; and `DeleteHideTest`. They cover:
  - no store for books with nothing to split;
  - a single rebuild, with 500s after it fails;
  - delete during a rebuild;
  - forget and drop paths;
  - positions, bookmarks and annotations stored original and drawn virtual;
  - an old unchunked row resolving;
  - a hit in a split section landing in the right part;
  - stats per layout.
- Device: `HugeChapterChunkTest`, run on the emulator, passes. It compares a control run (policy threshold
  `Int.MAX_VALUE`, unsplit) with a chunked run (default policy, 80 parts) of
  `stress-huge-single-chapter.epub`:
  - Resume from the control's position row lands on the same text.
  - The control's highlight is drawn on the same words, and its bookmark is marked.
  - Search hit #100 (0-based index 99) lands on the same word. Its mapped CFI equals the control's.
  - A highlight made there stores byte-identically the control's CFI.
  - A bookmark and the closing position made in the chunked run are byte-identical to the control's, in this run.

## Questions for the gatekeeper

1. **Which huge documents are split.** *Answered by C-050.* Only `application/xhtml+xml` spine items that an XML parser accepts
   (rules under `SplitPlanner` above) are split. `text/html` items, sloppy XHTML (`<br>`, `&nbsp;` without a
   doctype) and Shift_JIS-type encodings are served whole, as today. Such a book still opens, but slowly
   (P-014 is not met for it). For those documents the browser's HTML parser can see different child elements than
   the scanner, which would put saved positions and highlights on the wrong text. *Proposed default:* keep this
   rule (slow but correct). If a real book needs it, a later step can normalize such documents to well-formed
   XHTML before splitting, with its own position mapping.
2. **Nested wrappers.** *Answered by C-051.* One wrapper level is handled (`body > div > p…`). Deeper single-child chains
   (`body > div > div > p…`) are not split. *Proposed default:* accept for the MVP; extend if a real book needs it.
3. **CSS that depends on sibling position** *Answered by C-051.* (`:first-child`, `+`, `:nth-child`, counters) can style a part's first
   element differently than in the whole document (engine-evaluation §7). *Proposed default:* accept for the MVP.
4. **A highlight that crosses a cut** *Answered by C-052.* (saved under another policy, or across body-level elements before chunking
   existed) is shown only up to the end of its first part. The stored range is not changed. *Proposed default:*
   accept.
5. **Memory on the device.** *Answered by C-053.* Chunking keeps the decoded document and its text in memory for a moment (about 40 MB
   for 10 MB on the JVM, roughly double on Android, where strings are UTF-16). It runs once per book and policy;
   after that, opens read the cache. *Proposed default:* check it with P-061's peak in M9; reduce it only if it
   threatens 400 MB.
6. **No schema 8.** The brief said "`book_cache` is schema version 8 (AutoMigration 7->8)". `book_cache` exists
   since schema 4, and nothing in 8.3 needs a schema change: the layouts differ by `kind`, and the chunk cache checks
   itself. *Proposed default:* the schema stays at 7, and version 8 is free for the next track that needs one.
7. **P-061 peak 629 MB on the first open of the huge chapter** (Must 400; steady 217 MB passes). *Proposed
   default:* in M9 (C-053), split the peak between chunking (no counter) and the page counter's layout of 80 parts.
   If it is the counter, count huge books part by part or later.
8. **Fractions in the chunked layout.** CFIs and section indices are stored as original values. The fraction stored
   with a position or bookmark is foliate's fraction over the virtual sections: close to the unchunked value, but
   not equal. It is only displayed (slider, bookmark list). *Proposed default:* accept.
9. **Highlight under the search outline.** A highlight on exactly the shown search hit's range is drawn as the
   outline until the search highlight is cleared (one overlay per CFI in foliate). It then reappears; that redraw is
   the M6 bug fixed here. *Proposed default:* accept.
10. **P-020 method.** The video starts at the first visible change (the panel's label). Making the label faster makes
    P-020 read worse, even when the page arrives no later. *Proposed default:* in M9, also record command ->
    `painted` (or tap -> page) next to the video number before reworking P-020.
11. **Chunk cache per path.** The same file at two paths, or a moved file, is chunked once more (about 0.5 s on the
    huge chapter). The old directory is left for the system to trim. *Proposed default:* accept.
12. **Other corpus books may now be split.** `linear-algebra.epub` (P-043) has XHTML files over 512 KB. P-043 was not
    in this milestone's set. *Proposed default:* M9's full run covers it.
