      first page then 200, hit offsets from `highlight()`, ~200-char snippets, cap 5000 → "5000+")

      `ReaderController.searchFor(text)` as the F-051 entry point, index and history removed with the book

## Other checks on the device

- Instrumented suite, final code: **47/47 pass** (`am instrument`, all classes), including `SearchFlowTest`
  (Borodinó → 108 hits, jump lands in the hit's section with the highlight drawn; MARKERWORDMANY → 1 hit labelled
  chapter 1777; a hit in the preloaded next section is highlighted after the swap — S2) and the S2
  `ReaderBoundaryTest`.
- First device run found a real bug: a search started just as the index build finished returned 0 hits (the reader
  connection read the index metadata before setting `busy_timeout`, so the builder's closing checkpoint made it look
  unusable). Fixed in f1b2901 with a pinning test.
- Opening the search panel shows the keyboard; the page under it does not move (page 29 before and after, API 37).
- The hit highlight is clearly visible on the Light and Dark themes (checked by eye).

## Deviations

- A search runs when the user submits (keyboard search action, a history entry, or the chip), not on every keystroke.
  The benchmarks measure from the search command; live search can come later if wanted.
- The idle/charging WorkManager job is unit-tested (selection, skips, failure isolation) but was not exercised on the
  device (needs idle + charging). WorkManager no longer initialises at app start (on-demand), so cold start is unchanged.
- Each hit is one FTS5 highlight span: overlapping phrase occurrences ("the the" in "the the the") count once, and a
  phrase split across an 8,000-character extraction segment boundary is not found.

## Questions for the gatekeeper

- **Q1 (keyboard on Android 8-9-10, API 26-29).** The activity uses `adjustResize`. On API 30+ (verified on API 37) the
  keyboard only adds insets and the page stays put. On API 26-29 the window may resize when the search keyboard opens,
  which could re-lay-out the page behind the panel. No such device or image is set up. Proposed default: check it in
  the M9 real-device pass and switch the reader to `adjustNothing` + `imePadding` if it moves.
- **Q2 (scripts without spaces).** `unicode61` does not split Chinese/Japanese/Thai text into words, so in those
  books a search matches only from the start of a run of characters, and snippets around such hits have little
  context. F-050 doesn't mention these scripts. Proposed default: leave as is for the MVP; revisit with a corpus check
  of the Japanese samples if wanted.
